# Безопасное продолжение разработки VeyrArc

Актуально на 30 октября 2026. VeyrArc полностью бесплатен: без тарифов, оплаты и реферальных вознаграждений.

## Среды и ветки

- Рабочая ветка — `veyrarc-app`, сайт — https://veyrarc.onrender.com. Render собирает `app`: `npm ci && npm run build`.
- Исправления готовятся в `fix/free-app-reliability`. Эта ветка не должна назначаться рабочему сервису Render.
- Ранее в документах утверждалось, что staging имеет отдельную базу и что автодеплой production выключен. Это не подтверждено проверкой конфигурации Render. Не полагаться на эти утверждения.
- Локальные тесты используют только loopback или временную базу PGlite в памяти. Доступ к действующей базе для тестов не нужен.
- Для размещённого staging необходимы отдельный проект Supabase, тестовые пользователи и отдельный Render-сервис. Копировать реальные пользовательские данные и production-секреты нельзя. Создание и публикация среды — отдельный шаг, ещё не выполненный.

## Локальная проверка

Node 22.18+ (ветки 22/24), версии закреплены в `.node-version`; зависимости — `app/package-lock.json`.

```sh
cd app
npm ci
VITE_DEMO=1 npm run check
npx playwright install chromium
VITE_DEMO=1 npm run test:ui
```

`check`: строгая проверка TypeScript, тесты очереди/импорта/изоляции конфигурации/пагинации/голосовых намерений, настоящие SQL-транзакции и RLS в PGlite, production-сборка. `test:ui`: Chromium, мобильный и настольный размеры, основные экраны и старые ссылки. Демоверсия не должна содержать переменные Supabase. Автоматические проверки добавлены в `.github/workflows/check.yml`; в workflow нет деплоя.

PGlite не заменяет проверку GoTrue, PostgREST, Edge Functions и браузерной авторизации на отдельной Supabase. Старые `tools/e2e-*.mjs` с регистрацией требуют полноценного локального стека и не входят в стандартный smoke-тест. Их общие helpers запрещают внешний APP_URL.

## Изоляция staging

При подготовке отдельной среды задаются:

```dotenv
VITE_APP_ENV=staging
VITE_STAGING_SUPABASE_REF=<ref отдельного тестового проекта>
VITE_SUPABASE_URL=https://<тот же ref>.supabase.co
VITE_SUPABASE_ANON_KEY=<публичный ключ только тестового проекта>
VITE_SITE_URL=https://<отдельный staging-сайт>
```

Сборка отклоняет известный рабочий ref `lvmglqnzlvvfeqruqouj`, отсутствие явного staging-ref, несовпадение адреса, HTTP для размещённой базы и смешение деморежима с ключами. Локальный режим допускает только loopback. Service-role ключ никогда не передаётся в `VITE_*`. На стороне Supabase отдельно настраиваются разрешённые Auth redirect URLs; на Render исключается общий env group с production-секретами. Проверить настройки до первого запуска. Связь доступного Supabase-проекта с действующим Render должна быть отдельно подтверждена.

## База данных и порядок будущего выпуска

В доступной базе уже есть таблицы, но журнал Supabase migrations пуст. **Нельзя запускать всю историю миграций поверх этой базы.**

1. Проверить точное соответствие Render → Supabase и выгрузить схему/права/триггеры только для чтения. Сделать проверенную резервную копию перед изменениями production.
2. На отдельной базе проверить актуальную схему и новый файл `20261030075328_free_app_reliability.sql`. Согласовать baseline с реальной схемой; не отмечать отсутствующие миграции выполненными без сверки.
3. Новый SQL отключает коммерческие API/триггеры, даёт всем одинаковое количество заморозок, закрепляет search_path и добавляет транзакционные `apply_my_operations` и `import_my_data` с RLS и квитанциями повторных запросов. Пользовательские записи не удаляются. Старые SQL-файлы оплаты/рефералов сохранены как история; новый SQL отключает их поведение.
4. Единственное исправление старого SQL — `create schema if not exists private` перед созданием timeline-функций: чистая база ранее не разворачивалась без неявного предварительного шага.
5. Проверить на отдельной Supabase: регистрация, вход/выход, смена аккаунта с очередью, повторный вход после перезапуска, импорт/экспорт, фоновые уведомления, офлайн → онлайн. Распознавание речи пользователь уже проверил; автоматический разбор намерений также проверяется.
6. Только после отдельного разрешения владельца: применить проверенный новый SQL к рабочей базе, затем выпустить совместимый frontend. **Не публиковать новый frontend раньше RPC:** создание цели с шагами и другие составные операции зависят от него. Проверить статус и логи. Слияние в `veyrarc-app` тоже требует решения о выпуске, поскольку фактический режим автодеплоя не подтверждён.
7. Откат frontend — предыдущий проверенный коммит. Новые таблицы/функции оставить для совместимости, не удалять пользовательские данные. Старый frontend может показывать устаревшие платные элементы; это временный технический откат, не возврат платной модели.

## Оставшиеся административные пункты

На размещённой Supabase проверить защиту от скомпрометированных паролей (доступность зависит от плана) и размещение `pg_net` согласно рекомендациям расширения. Не переносить расширение вслепую. Настроить обязательный успешный CI и запрет прямой записи в рабочую ветку. Эти настройки внешних сервисов в данном изменении не менялись.

При ошибке отправки операции пользователь получает уведомление; отклонённые операции сохраняются в `veyrarc.queue.<user-id>.failed` для диагностики. Их не переотправлять вслепую после изменения схемы. Не очищать localStorage до сохранения ожидающих изменений. Корректная очередь другого аккаунта сохраняется отдельно и отправляется только после входа владельца.
